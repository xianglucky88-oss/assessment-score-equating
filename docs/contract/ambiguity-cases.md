# 契约歧义暴露：最小矛盾例

本文件用一组**最小**输入暴露当前契约中的歧义。每个用例都给出两种各自合理、
但**互相矛盾**的契约解读；当前代码默默地实现了其中一种（或直接崩溃），而
README 与代码注释都不足以裁决。用例输入在 `fixtures/contract/`，输出快照在
`fixtures/contract/snapshots/`，全部【已验证】（快照由当前代码实际生成，可用
`python3 tools/regen_contract_snapshots.py --check` 复核）。

这些用例的用途不是"展示 bug"，而是**迫使评审做出裁决**：每个用例末尾的
"待裁决问题"必须在校准契约时给出答案，并记入变更记录。裁决前，任何一方解读
都不得当作契约事实引用。

贯穿全部用例的元矛盾：**代码的严格性没有一致原则**——对非 dict 行静默宽容
（case-05a），对缺 `item` 字段硬崩溃（case-05b），对未声明的 form 静默给
缺省量尺（case-06），对未知字段静默忽略（case-08）。维护者不能从任一用例
归纳出"本系统遇到异常输入时会如何"，必须逐点裁决。

## case-01 被作废"清空"的考生去了哪里

输入：S1 答 Q1（有效），S2 只答了 Q2，而 Q2 被作废。
快照：`case-01-voided-out-student.expected.json` —— `scores` 只有 S1 一行。

- 解读甲：每个考生都应有一条成绩记录，全部作废则 `raw=0, attempted=0`。
- 解读乙：没有可计分作答即没有记录，考生不出现在输出中。
- 代码实际：解读乙（engine.py:4-5，作废行在分组前被跳过，分组键从不建立）。
- 矛盾点：若下游按"输出人数 == 应考人数"对账，解读甲下成立、解读乙下静默缺人。
- 待裁决：缺考/全作废考生应"消失"还是"0 分记录"？（与 C 类变更直接相关）

## case-02 缺键题上，`null` 作答反而得分

输入：Q9 无评分键；S1 答 `null`，S2 答 `"A"`。
快照：`case-02-missing-key-null-answer.expected.json` —— S1 `raw=1`，S2 `raw=0`。

- 解读甲：无键题不可评分，任何作答都不得分（或应报错）。
- 解读乙：缺键按"正确答案是 `null`"处理，答 `null` 者得分。
- 代码实际：解读乙（engine.py:5，`keys.get(item)` 返回 `None`，`None == None` 为真）。
- 矛盾点：同一道"无键题"，具体作答与空作答结果相反；"删键"与"键设为 null"
  在当前代码下行为相同，但管理意图相反。
- 待裁决：缺键题的计分语义；`null` 作答的合法性；删键与 null 键是否需区分。

## case-03 重复作答行被重复计分

输入：S1 对 Q1 的两行完全相同的作答。
快照：`case-03-duplicate-response-rows.expected.json` —— `attempted=2, raw=2, scale=20`。

- 解读甲：一题一答，重复行是数据错误，应去重或报错。
- 解读乙：作答是流水，每行都计入。
- 代码实际：解读乙（engine.py:5，无去重逻辑）。
- 矛盾点：`scale=20` 超出了"满分 10"的直觉量尺上限；上游若重传数据，成绩
  静默翻倍，无任何告警。
- 待裁决：重复行的定义（完全相同？同题不同答？）与处置（去重/报错/保留）。

## case-04 舍入：1.125 不进位，2.675 少进位

输入：三个 form 量尺分别为 1.125、2.675、1.005，各 1 题答对。
快照：`case-04-rounding-boundary.expected.json` —— `1.12`、`2.67`、`1.0`。

- 解读甲：日常"四舍五入"——1.125→1.13，2.675→2.68，1.005→1.01。
- 解读乙：Python `round()` 的银行家舍入 + 二进制浮点——1.125→1.12（half-even），
  2.675→2.67（浮点表示为 2.67499…），1.005→1.0（浮点表示为 1.00499…）。
- 代码实际：解读乙（engine.py:7）。
- 矛盾点：1.125 与 2.675 同样"第三位是 5"，一个按 half-even 一个按浮点误差
  处理，**规则本身不统一**；考生/家长按解读甲复算会得出不同分数。
- 待裁决：舍入规则的书面定义（模式、精度、是否十进制运算）；D 类变更的断点政策。

## case-05a/05b 异常输入：静默丢弃 vs 硬崩溃

输入 05a：`responses` 中混入字符串 `"not-a-dict"` 和数字 `42`。
快照：`case-05a-non-dict-row.expected.json` —— 正常输出，坏行被丢弃。
输入 05b：作答行缺 `item` 字段。
快照：`case-05b-missing-item-field.expected.error.txt` —— `ERROR KeyError: 'item'`，
无 JSON 输出，进程崩溃。

- 解读甲：输入校验应一致——要么全部宽容（跳过坏数据），要么全部严格（报错）。
- 解读乙：结构错误（非 dict）可跳过，字段缺失是硬错误。
- 代码实际：两者皆非的一致版本不存在——parser.py:5 静默过滤非 dict 行，
  engine.py:4 对缺 `item` 直接 `KeyError`；而 `responses` 整个不是 list 时
  又是第三种行为（`ValueError`，parser.py:3-4）。
- 矛盾点：同类"坏输入"有三种处置；调用方无法写出统一的错误处理。
- 待裁决：输入校验矩阵（每种异常 → 丢弃/报错/缺省），以及是否需要错误包络。

## case-06 未声明的 form 静默使用缺省量尺 10

输入：S1 的 form 是 F9，但 `scale` 只声明了 F1=12。
快照：`case-06-undeclared-form-scale.expected.json` —— `scale=10`（raw×10）。

- 解读甲：每个 form 必须显式声明量尺，未声明应报错。
- 解读乙：未声明的 form 用缺省乘数 10。
- 代码实际：解读乙（engine.py:7，`scale.get(form, 10)`）。
- 矛盾点：新 form 上线忘配量尺时无任何告警，成绩按错误量尺发布；与 case-05b
  的"缺字段即崩溃"原则直接冲突。
- 待裁决：缺省量尺 10 是契约还是意外？未声明 form 的处置。

## case-07a/07b 键修订无痕：两份输出都无法自证来源

输入：同一批作答，`keys.Q1` 分别为 `"A"`（07a）与 `"C"`（07b），考生答 `"C"`。
快照：`case-07a-scoring-key-before.expected.json`（`raw=0`）与
`case-07b-scoring-key-after.expected.json`（`raw=1`）。

- 解读甲：成绩报告应能说明自己基于哪版评分键。
- 解读乙：输出是纯结果，来源靠外部归档。
- 代码实际：解读乙——输出顶层键只有 `project/scores/status/void_items`，
  两份输出除分数外逐字节相同，无任何版本或时间字段。
- 矛盾点：键修订后重跑历史场次，新报告覆盖旧报告且无法区分；复核（当前不
  存在的环节）即使将来加入，也没有可引用的版本锚点。
- 待裁决：输出是否及如何携带键版本/载荷版本（属契约新增，L2）。

## case-08 写入 `status` 字段：静默无效的"缺考标记"

输入：作答行带 `"status": "absent"`。
快照：`case-08-extra-status-field.expected.json` —— 成绩照常计算，`raw=1`。

- 解读甲：标记缺考的行应不计分（或报错"未知字段"）。
- 解读乙：未知字段被忽略，行照常计分。
- 代码实际：解读乙（engine.py:4-5 只读 `item/student/form/answer` 四个键）。
- 矛盾点：上游系统若已开始发送 `status`，当前管线**静默给出与发送方意图相反
  的结果**——标了缺考的人得了分。这是 C 类变更必须拦截的陷阱。
- 待裁决：未知字段策略（忽略/拒绝/告警）；缺考与违规的一等表示（见兼容矩阵 C）。

## case-09 作废表回显包含从未出现的题

输入：`void_items` 含 Q99（无任何作答）和 Q1（S1 唯一作答）。
快照：`case-09-void-echo-unseen-item.expected.json` —— `scores` 为空，
`void_items` 回显 `["Q1", "Q99"]`。

- 解读甲：输出 `void_items` 是"本次实际作废生效的题"。
- 解读乙：输出 `void_items` 是输入作废表的排序回显，与作答无关。
- 代码实际：解读乙（engine.py:8）。
- 矛盾点：下游若按解读甲统计"受影响题目数"会高估；同时 `scores` 为空但
  `status` 仍是 `"ok"`，"全场作废"与"正常场次"在包络上不可区分。
- 待裁决：`void_items` 回显的语义；空 `scores` 是否需要包络层面的信号。

## case-10 同样的 10 分，`10` 与 `10.0` 两个文本

输入：form FI 量尺为整数 `10`，form FF 量尺为浮点 `10.0`，各 1 题答对。
快照：`case-10-int-vs-float-scale.expected.json` —— S1 `scale: 10`，
S2 `scale: 10.0`。

- 解读甲：`scale` 是数值，文本表示应统一。
- 解读乙：文本表示随输入乘数类型漂移。
- 代码实际：解读乙（`round(int, 2)` 返回 int，`round(float, 2)` 返回 float，
  JSON 序列化保留各自表示）。
- 矛盾点：按文本 diff 的下游流程（含本仓库快照比对）会把纯输入类型变化
  报成"成绩变化"；按值消费的下游则无感。
- 待裁决：`scale` 的输出类型是否归一（属 D3 变更）；快照比对按值还是按文本。
